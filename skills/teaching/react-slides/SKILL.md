# React slides

You are the **coordinator**. You talk with the user, run the script, dispatch the illustrator, capture screenshots, build the app and check it in a browser. Talk with the user in their language. Code, file names and the report's paths stay as they are.

The input is a `slide-design` deck (`slide-design/deck@1`) and the course's visual vocabulary (`slide-design/vocabulary@1`). The output is the course's web app, `<course_dir>/web/`: a Vite + React + TypeScript app with a home page of Part cards and one slide deck per Part.

All paths below are relative to this skill's base directory (the directory this file was loaded from), written `<skill>/…`. `<course_dir>` is the course folder, `<cwd>/courses/<slug>/`. `<N>` is the Part number and `NN` is that number with two digits (`part-01`, `part-10`). `<web>` is `<course_dir>/web` and `<work>` is `<web>/_work/part-NN`, which is git-ignored and never bundled.

**Never deploy.** The run ends with a built `dist/` that the user deploys where they like.

The skill **never changes slide text**, code or output. The slides show the deck's text exactly. When text does not fit, that is a template problem to report, not text to shorten.

The run stops for the user only for decisions that are theirs: overwriting a file they edited, and a deck that cannot be read. Everything else runs without stopping to ask. Every step can be repeated safely: on resume, the manifest (`<web>/.react-slides.json`), `<work>/visuals.json` and the files present say what is done.

## Step 0: check the inputs

`build_part.py` checks the inputs itself: the deck and vocabulary templates, every layout, required field, diagram, element and snippet, and that each code excerpt equals its snippet's lines. It also needs `node` and `npm` on `PATH` (Node.js 20 or later).

When the deck is **stale** (its `source_sha256` no longer matches the Part file), the report warns. Tell the user and suggest redoing the deck with `slide-design`, then carry on: the deck is still valid on its own.

## Steps 1–2: scaffold, upgrade and convert

```bash
python3 <skill>/scripts/build_part.py <course_dir> <N>                  # this Part only
python3 <skill>/scripts/build_part.py <course_dir> --all                # every Part that has a deck
python3 <skill>/scripts/build_part.py <course_dir> <N> --force <path>   # overwrite one skipped file (repeatable)
python3 <skill>/scripts/build_part.py <course_dir> <N> --skip-install   # do not run npm install
```

On the first run it copies the template into `<web>`, writes `src/course.ts` from the overview's title, and runs `npm install`. Later runs apply template upgrades and run `npm install` when `package.json` changed. It writes `src/parts/part-NN.tsx` and `part-NN.data.ts`, `src/vocabulary.ts`, and `<work>/visuals.json`, then prints a JSON report on stdout.

Act on the report:
- **Exit status 1 with `error:` lines:** the deck cannot be read, so nothing was written. Show the user every error, point them to `slide-design` (its `validate_deck.py` names the same problems), and stop.
- **`skipped`:** files the user edited. They are kept. `diffs` shows what the new version would change. Ask the user, per file, whether to overwrite it; for each yes, run again with `--force <path>`. A Part's `.tsx` and `.data.ts` are skipped together, and forcing either one overwrites both.
- **`warnings` and `stale`:** pass them on in the report. Unsupported markup is shown as written.
- **`older_parts`:** other Parts were generated by an older version. Offer `--all`, which regenerates only their unedited files.
- **`visuals`:** the illustrations and screenshots for Steps 3 and 4. `exists` is true when a file is already there.
- **`unused`:** files no slide uses any more. They are never deleted; list them.
- **`install`:** `ran`, `skipped` or `not-needed`.

## Step 3: illustrations

When `<work>/visuals.json` lists an illustration with `exists` false, dispatch one illustrator for the Part, with `subagent_type="general-purpose"` and no `model`:

```
Draw the illustrations for Part <N> of the course in <course_dir>.

Inputs: <course_dir>/web/_work/part-NN/visuals.json, <course_dir>/web/src/vocabulary.ts
Output: one file per illustration key at <course_dir>/web/src/illustrations/part-NN/<key>.tsx

As a first step, read <skill>/references/illustrator.md and follow it.
```

The reply lists `Drawn:` and `Skipped:` keys. A skipped illustration keeps the deck's fallback; the report lists it with its `prompt`, so the user can add an image later at `src/assets/images/part-NN/<key>.png` (or `.jpg`, `.webp`), which takes precedence over a drawing. Check each drawing in Step 5 and allow one redo: the same prompt plus `Redo mode. Redraw only these: <key> — <what is wrong>`.

## Step 4: screenshots

With a browser tool, capture each screenshot in `visuals.json` whose `exists` is false, only when its `url` is a public page that needs no login, no account and no personal data:
1. Open the `url` at 1280 × 800 and do what `capture` says: scroll, or open public navigation. Close a cookie banner if it covers the content.
2. Save the screenshot to `<web>/<path>` (the entry's `path`, a `.png`).

Public pages only: never sign in, never create an account, never type credentials, never fill in a form and never accept terms on the user's behalf. When in doubt, keep the fallback. Every screenshot not captured keeps its fallback and goes in the report.

## Step 5: build and check

1. `npm --prefix <course_dir>/web run build` must pass. It runs `tsc --noEmit` and the Vite build. When it fails, stop and report the failing file and the error: an edited file that no longer compiles is the user's to fix, or to replace with `--force`. An illustration that fails goes back to the illustrator.
2. `npm --prefix <course_dir>/web run preview`, in the background. It serves the build at `http://localhost:4173/` (it prints another port when that one is busy).
3. Open `http://localhost:4173/#/check/part-NN` and wait until `window.__reactSlidesCheck.done` is true. Read its `findings`.
4. Take screenshots of every slide with a finding, and one slide of each layout, at `http://localhost:4173/#/part-NN/<slide id>`, and look at them.
5. Fix what can be fixed in the illustrations, rebuild and check once more.

`references/visual-check.md` says what each finding means and what may be fixed. Text overflow that the template's auto-fit cannot absorb is a template defect: it goes in the report and in `skill-problems.md`.

## Step 6: report

Tell the user, briefly and in their language:
- the app path, `<web>`
- `npm run dev` in `<web>` to view it locally, and `npm run build` to get `dist/` for deployment (any static host; it works from a sub-path)
- the illustrations drawn and the ones that fell back, with their prompts
- the screenshots captured and the ones that fell back
- the files skipped because the user edited them
- the check findings that remain
- the stale-deck warning, `older_parts` and `unused` files, when there are any
- the skill-problems offer (below)

Point to the files. Do not paste the slides.

## Hand edits

The generated Part files are the user's to edit. `references/components.md` is the component API, for you and for them. Once a file differs from what the skill wrote, the skill skips it from then on and says so in the report.

## Without a subagent tool

When there is no Agent tool, do the illustrator's work inline, following `references/illustrator.md` exactly and writing the same files. The steps, the script and the checks stay the same.

## Without a browser tool

Skip the screenshots and the check page, and say so in the report: screenshots keep their fallbacks, and the slides were built but not looked at. `npm run build` still has to pass.

## Reporting problems with this skill

When something in this skill goes wrong or does not fit (a script error, a validator error that was wrong, a brief that misled a subagent, a limit or rule that did not fit real content), append one line to `<course_dir>/web/_work/part-NN/skill-problems.md` as soon as you see it:

`- <bug|improvement|docs> · <what happened> · <where: the script, brief or rule> · <stage>`

A subagent's `Skill problem:` line goes in too. On resume, read the file first. At the end of the run, if any line has no ` → ` mark yet, offer once to report them with the `report-skill-issue` skill, or at once if a problem stops the run. Then mark each line the offer covered: ` → <issue URL>` once reported, or ` → not reported (<date>)` if the user declined or dropped it. A marked line is never offered again. If `report-skill-issue` is not installed, list the unmarked lines in your final report instead.
