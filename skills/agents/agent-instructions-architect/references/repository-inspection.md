# Repository inspection

Inspect before designing. Use fast repository search and read configuration
files before prose guesses.

## Minimum evidence

Record:

1. repository type and monorepo topology;
2. package manager, languages, frameworks, ORM/database, and build system;
3. applications, packages, modules, dependency direction, and data ownership;
4. test, lint, format, type-check, build, schema, and targeted commands;
5. deployment, infrastructure, queues, caches, storage, and external services;
6. generated source, build output, coverage, vendored files, and files marked
   generated by comments or tooling;
7. root and nested `AGENTS.md`, `AGENTS.override.md`, `.agents/skills/`,
   runtime-native adapters, and custom-agent definitions;
8. README, contributing guidance, architecture docs, standards, references,
   decisions, plans, and API/schema documentation;
9. CI, hooks, linters, dependency-boundary checks, generators, and architecture
   tests;
10. dirty-worktree state and existing instruction changes that must be
    preserved.

Search common files such as `package.json`, workspace manifests, lockfiles,
`Makefile`, task-runner configs, compiler configs, ORM schemas, container files,
and `.github/workflows/`. Inspect scripts before documenting a command. Never
invent a conventional command that the repository does not define.

## Evidence map

Before creating files, map each discovered fact to its current authoritative
location. Note missing, conflicting, stale, duplicated, and mechanically
enforceable information. Reuse an existing authoritative document when it
already serves the intended responsibility.

If architecture or project conventions cannot be inferred reliably, report the
gap instead of manufacturing a standard. If runtime behavior is material, read
`runtime-compatibility.md` and verify changeable claims against primary
documentation.
